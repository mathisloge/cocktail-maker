= 6 Runtime View

This chapter walks through the Station's key scenarios at the level of its own building blocks (xref:building-blocks.adoc[]).
The wire-level exchange with a Pod inside any of these scenarios follows the patterns defined in the xref:system::protocol.adoc[System protocol concept] and is not repeated here.

== A Pod Connects

A Pod, physical or simulated, is discovered, assigned an identity, and queried for its device information before it becomes available for dispensing.
The UI reflects the new connection as soon as it is known.

How does a new Pod become available, and what happens when it speaks another protocol release?

A Pod on another protocol release stays unused, and the Operator UI shows something like "Protokoll 2.2.0, erwartet 2.1.0".
It doesn't hold back the other Pods, just like an unplugged one.
A Pod that never answers the device info may speak a release whose reply doesn't decode, and the log says so (xref:system::protocol.adoc#_versioning[System protocol versioning]).

Once a Pod is connected, the Station also brings the fill level of its dispensers up to date.
See <<A Pod Comes Back After a Power Loss>>.

== A Guest Mixes a Drink

A Guest browses the recipe catalog, selects a recipe and, if needed, a glass.
The Station scales the recipe to the chosen volume and executes it as a sequence of dispensing actions against the owning Pods, reporting progress back to the Guest until the mix succeeds or fails.

How does the order of a Guest turn into dispensing actions on the Pods?

The warning leaves a reserve of 20 mL, because the fill level is only a guide.
It doesn't block a drink, and it stays out of the way for a dispenser with no known fill level.

A Pod reports a pour that came up short as a pour with less than the requested amount, not as an error.
`DispenseFinished` says why.

[cols="1,3", options="header"]
|===
| Pour ended | What the Station does

| `Completed`
| Nothing more.

| `BottleEmpty`
| The bottle ran empty or the pump is blocked, which look the same. The Station asks for a refill and
pours the rest. See <<A Bottle Runs Empty and Gets Refilled>>.

| `TimedOut`
| The Pod's time limit of 30 s ended it. The Station pours the rest without asking, unless the pour
moved less than 20 mL. That points at a problem, so the pour then counts as an empty bottle.

| `StillShort`
| The trims ran out a few grams before the amount. The Station pours the rest without asking, unless
less than half of a pour above 20 mL came out. Below 20 mL the load cell is too coarse for that, so
only a pour with nothing at all counts. Such a pour then counts as an empty bottle.
|===

A rest of up to 1.5 mL ends the pour, because that is within the Pod's tolerance.
The Station ignores the `DispenseProgress` that arrives during a pour or a calibration run.

If a dispense fails or the Guest cancels partway through, the Station stops the remaining actions, sends an `EmergencyStop` to every Pod, and returns the Guest to a known-good screen naming the affected ingredient rather than a generic failure.

== A Bottle Runs Empty and Gets Refilled

A pour that counts as an empty bottle by the table above only makes the Station suspect that the bottle is empty.
It can't store 0 yet, because a blocked pump looks just the same and the bottle may still be full.
The suspected bottle counts as empty for the warning, and the Operator UI says "vermutlich leer".

How does the Station find out whether a bottle it suspects to be empty got refilled?

The dialog needs no PIN, because a Guest may stand at the machine.
Confirming without a refill changes nothing and only costs a dry run of about 6.5 s, after which the dialog comes back.
The dialog also offers to cancel the drink.
If the next pour doesn't end short, the suspicion was wrong and goes away by itself.

The Operator UI has a button of its own for each dispenser, behind the Operator PIN.
A rise counts as above.
Without a rise, the Operator is saying that the bottle is full, so the fill level goes back to the last 100 %.
This covers a bottle refilled while the Station was off, which the correction at connect can't see.

A bottle topped up without any button still shows, because the fill level always follows the reading.

== An Operator Calibrates a Dispenser

An Operator authenticates, opens the Operator UI, and works through up to three steps for a specific dispenser.
The load cell comes first, because the dispenser calibration measures with it, but it only needs doing once, when the load cell is fitted.
So the dispenser calibration can run on its own.
The exchanges follow the patterns from the xref:system::protocol.adoc[System protocol concept].

Which steps calibrate the load cell and a dispenser, and what does each step change?

The Station only chooses the run time and shows the measured amount.
The Pod derives the calibration from that run, uses it at once, and keeps it across power cycles.
So the Station needs to know nothing about motor steps, and the same flow works for pumps and valves.
A new run replaces the calibration.

The run pours real liquid, so a glass has to stand under the dispenser, and the Operator can stop it.
A longer run gives a more accurate calibration, because the load cell reads to about 1 g.
That is about 5 % at 20 mL and about 2 % at 50 mL.
The run time is 1 s to 30 s and starts at 15 s, and the Station hints at a longer run below 50 mL.
A run where next to nothing came out ends with a `DispenserEmpty` error and leaves the previous calibration in place.
That can also be a run that was simply too short for this dispenser.

== A Pod Comes Back After a Power Loss

The Station owns the fill level of every dispenser (xref:system:adr:007-calibration-and-fill-level.adoc[SYS-007]).
A load cell takes whatever stands on it as its zero point at every power up, so a half full bottle then reads about 0 g.
Both calibrations survive, and pouring keeps working, because the Pod only looks at how far the weight falls.
Only the fill level needs a correction.

How does the Station correct the fill level after a load cell took a new zero point?

When only the Pod's controller restarted, the load cells kept their zero point.
The correction then comes out as it was before, and the fill level stays right.
A read that fails at connect is made up for at the next read.
A dispenser without a load cell has no fill level, and that is normal.

The Station therefore:

* Keeps the last fill level of every dispenser on disk, together with the last 100 % and the lowest level since then.
* Stores a fill level of 0 after taring an empty bottle.
* Writes that file in one step, on a thread of its own, so a power loss leaves a whole file and nothing blocks the Pods.
